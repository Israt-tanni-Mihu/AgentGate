# Design patterns in AgentGate

Rule: every pattern here is tied to a requirement. A pattern without a requirement does not belong in this table.

| Pattern | Requirement it serves | Participating classes | Alternative rejected (and why) |
|---|---|---|---|
| **Adapter** | FR1 — import REST tools from an OpenAPI file; QA5 — a classmate adds a new tool with no code changes. The import must stay open to other spec formats (e.g. Postman collection, an MCP server's `tools/list`). | Target: `registry.importer.ToolSpecAdapter` · Adapter: `OpenApiToolSpecAdapter` (OpenAPI 3 JSON → `ToolDefinition`) · Client: `ToolImportService` (picks the first adapter whose `supports()` is true, upserts by name) · Format-neutral data: `ToolDefinition`, `AdaptedSpec` | **Parse OpenAPI directly inside `ToolImportService`** — simpler today, but every new format would mean editing the import/upsert logic (violates Open/Closed). **swagger-parser library** — full spec support, but a heavy dependency for the subset we need (operationId, parameters, JSON body, local `$ref`); can be put *behind* the same interface later without touching the client. |
| **Adapter** | FR2 — agents authenticate with OAuth2 client credentials; agents are stored in *our* `agents` table (with clearance + enabled flag) and can be disabled at runtime through the admin API. | Target: Spring Authorization Server's `RegisteredClientRepository` · Adapter: `identity.AgentRegisteredClientRepository` (`Agent` row → `RegisteredClient`, disabled agent → "not found") · Adaptee: `AgentRepository` / `Agent` · Client: Spring Authorization Server's token endpoint (`/oauth2/token`) | **`JdbcRegisteredClientRepository`** (the framework's own `oauth2_registered_client` table) — works, but stores many fields we never use (redirect URIs, consent settings…) in a framework-owned schema, and clearance/enabled would need a second table kept in sync. **In-memory clients from `application.yml`** — no runtime registration or disabling, so it cannot meet FR2's admin API or FR8's kill switch. |
| **Chain of Responsibility** | Core call pipeline (FR3 now; FR4 approval, FR5 guards, FR6 limits, FR7 audit, FR8 kill switch later). Every call must pass an ordered series of checks, and adding a check must not mean editing existing ones (Open/Closed; C10 change request). | Handler: `pipeline.CallStep` (`handle(call, chain)`) · Chain: `pipeline.CallChain` · Runner: `pipeline.CallPipeline` (gets all `CallStep` beans sorted by `@Order`, see `CallStepOrder`) · Concrete handlers: `policy.PolicyStep` (allow → `chain.proceed`, deny → stop), `pipeline.ForwardStep` (last, calls the tool) | **One big `CallService` method with if-blocks per check** — simplest today, but every new FR edits the same method and its tests. **Spring AOP / servlet filters** — would work for cross-cutting concerns, but the order and the "stop with a reason" result are hidden in framework config; steps also need the parsed tool and identity, which filters do not have. **Simple `List<Check>` returning boolean** — cannot wrap the rest of the chain, so audit (FR7) could not see the final outcome and latency. |
| **Strategy** | FR3 — argument conditions in policies (`amount ≤ 2000`, `id` matches the end user …); new kinds of conditions must be addable without touching the engine. | Strategy: `policy.operator.ConditionOperator` · Concrete strategies: `EqualsOperator`, `NotEqualsOperator`, `LessThanOrEqualOperator`, `GreaterThanOrEqualOperator`, `InOperator`, `MatchesEndUserOperator` · Context: `policy.PolicyEngine` (picks the operator by the `operator` name in the rule JSON; Spring injects all operator beans) | **`switch (operator)` inside the engine** — shorter, but every new operator edits and re-tests the engine, and per-operator value checks/explanations end up scattered. **A general expression language (SpEL)** — very flexible, but an admin-written expression can call arbitrary methods (security risk in a security product) and is hard to validate or explain in a deny message. |
