Rule: every pattern here is tied to a requirement and points to real code and a real test. Package root: `gateway/src/main/java/com/agentgate/gateway/` (shortened below to the package name, e.g. `pipeline.CallPipeline`). Tests live under `gateway/src/test/java/com/agentgate/gateway/`.

**Notes (honest gaps):**
- **Proxy:** there is no class-level GoF Proxy (a class with the same interface as the real tool standing in for it). The gateway is a proxy at architecture level only. `ResilientForwardStep` has the same interface as its target but *adds behaviour*, so it is listed as Decorator.
- **Command: not implemented.** `pipeline.ToolCall` is an immutable data record (tool, arguments, identity). It has no `execute()`/`undo()`; the pipeline acts on it. It is a parameter object, so it is not claimed as Command. Approvals store the call's arguments as data, not as a replayable command object.

## Extension proof: a new guard = one new bean

How to add a guard: write a `@Component` class that implements `CallStep`, put `@Order(CallStepOrder.X)` on it, and add one constant to `CallStepOrder`. `CallPipeline` receives `List<CallStep>` from Spring already sorted, so no existing step changes. Real example, `admin/KillSwitchStep.java` (shortened):

```java
@Component
@Order(CallStepOrder.KILL_SWITCH)          // 100 = first step
public class KillSwitchStep implements CallStep {
    public CallOutcome handle(ToolCall call, CallChain chain) {
        if (state.isAgentKilled(agentId)) return new CallOutcome.Denied("kill-switch-agent", ...);
        ...
        return chain.proceed(call);
    }
}
```

Proof at runtime: on startup `CallPipeline` logs `Call pipeline: [KillSwitchStep, ToolAvailabilityStep, LimitStep, ...]`. Proof in the build: the ArchUnit rule `ArchitectureTest.pipeline_steps_do_not_depend_on_each_other` fails if a step depends on another concrete step (only named exception: `ApprovalStep` re-runs `SchemaValidationStep` and `PolicyStep` on edited arguments).

## Note: why the audit log has ONE writer thread (FR7, QA2, QA3)

`AuditWriter` puts each `CallCompleted` into a single-threaded executor (`audit-writer`).

- **The chain cannot fork.** Each record's hash needs the hash of the record before it (`hash = SHA-256(prevHash + canonical JSON)`). With two writers, two records could both take the same "previous" record and the chain would split. One writer adds records strictly one after the other, so `seq` and `prev_hash` are always correct.
- **No added latency for the agent (QA2).** The agent's thread only drops the event into the queue and returns. Redaction, hashing and the database insert all happen on the writer thread.
- **Cost:** records appear a few milliseconds after the call ends (`AuditVerifier` first waits for the queue to drain, so `verify` is still exact), and a crash can lose events that are still queued. Failed inserts are retried 3 times, then logged as `AUDIT RECORD LOST`.
- **Limit:** this design assumes ONE gateway instance. A second instance would write to the same table and could race; the primary key on `seq` makes that fail loudly instead of forking silently. Scaling out would need a lock or a dedicated audit service (candidate ADR).
- **Rejected:** a database lock around "read last hash + insert" on the call thread (correct, but every call waits in line for the previous insert, which could hurt the 30 ms p95 goal at 100 calls/s; not measured yet).

**Read side (search and export):** `AuditSearchService` and `AuditExporter` only read; the `AuditRecord` entity is `@Immutable` and the repository has no write methods, so no code path can edit or delete a record over the API.

**What the hash chain cannot detect:** deleting the **last** rows (nothing after them points back to them), or rebuilding the whole chain from the start with new hashes. Ways to reduce this risk: (1) copy the latest `seq` + `hash` to a place the database admin cannot write (a file, another system, a signed e-mail) and compare it during `verify`; (2) sign the hash with a key kept outside the database; (3) give the application's database user INSERT and SELECT only, no UPDATE or DELETE. None of the three is built yet (candidate ADR).
