# Design patterns in AgentGate

Rule: every pattern here is tied to a requirement. A pattern without a requirement does not belong in this table.

| Pattern | Requirement it serves | Participating classes | Alternative rejected (and why) |
|---|---|---|---|
| **Adapter** | FR1 — import REST tools from an OpenAPI file; QA5 — a classmate adds a new tool with no code changes. The import must stay open to other spec formats (e.g. Postman collection, an MCP server's `tools/list`). | Target: `registry.importer.ToolSpecAdapter` · Adapter: `OpenApiToolSpecAdapter` (OpenAPI 3 JSON → `ToolDefinition`) · Client: `ToolImportService` (picks the first adapter whose `supports()` is true, upserts by name) · Format-neutral data: `ToolDefinition`, `AdaptedSpec` | **Parse OpenAPI directly inside `ToolImportService`** — simpler today, but every new format would mean editing the import/upsert logic (violates Open/Closed). **swagger-parser library** — full spec support, but a heavy dependency for the subset we need (operationId, parameters, JSON body, local `$ref`); can be put *behind* the same interface later without touching the client. |
| **Adapter** | FR2 — agents authenticate with OAuth2 client credentials; agents are stored in *our* `agents` table (with clearance + enabled flag) and can be disabled at runtime through the admin API. | Target: Spring Authorization Server's `RegisteredClientRepository` · Adapter: `identity.AgentRegisteredClientRepository` (`Agent` row → `RegisteredClient`, disabled agent → "not found") · Adaptee: `AgentRepository` / `Agent` · Client: Spring Authorization Server's token endpoint (`/oauth2/token`) | **`JdbcRegisteredClientRepository`** (the framework's own `oauth2_registered_client` table) — works, but stores many fields we never use (redirect URIs, consent settings…) in a framework-owned schema, and clearance/enabled would need a second table kept in sync. **In-memory clients from `application.yml`** — no runtime registration or disabling, so it cannot meet FR2's admin API or FR8's kill switch. |
| **Chain of Responsibility** | Core call pipeline (FR3 policy, FR5 guards; FR4 approval, FR6 limits, FR7 audit, FR8 kill switch later). Every call must pass an ordered series of checks, and adding a check must not mean editing existing ones (Open/Closed; C10 change request). | Handler: `pipeline.CallStep` (`handle(call, chain)`) · Chain: `pipeline.CallChain` · Runner: `pipeline.CallPipeline` (gets all `CallStep` beans sorted by `@Order`, see `CallStepOrder`) · Concrete handlers: `guard.SchemaValidationStep` (before the policy: rejects malformed arguments), `policy.PolicyStep` (allow → `chain.proceed`, deny → stop), `pipeline.ForwardStep` (last, calls the tool), and the result guards that wrap the forward call: `guard.OwnershipCheckStep` → `guard.RedactionStep` → `guard.TruncationStep` (each inspects or rewrites the result after `chain.proceed` returns). FR5 added 4 beans and 4 `CallStepOrder` constants and edited no existing step: a result guard's code after `proceed` runs in reverse order, so the lowest number handles the result last. FR6/FR8 added 2 request-side beans without editing any existing step: `admin.KillSwitchStep` (order 100, first) and `limits.LimitStep` (order 150, before the schema check). | **One big `CallService` method with if-blocks per check** — simplest today, but every new FR edits the same method and its tests. **Spring AOP / servlet filters** — would work for cross-cutting concerns, but the order and the "stop with a reason" result are hidden in framework config; steps also need the parsed tool and identity, which filters do not have. **Simple `List<Check>` returning boolean** — cannot wrap the rest of the chain, so audit (FR7) could not see the final outcome and latency. |
| **Strategy** | FR5 — personal data is masked differently per data type (e-mail, Bangladeshi phone, national ID), and which types each clearance sees is configuration; a new data type must be addable by writing one class. | Strategy: `guard.redaction.DataRedactor` · Concrete strategies: `EmailRedactor`, `PhoneRedactor`, `NationalIdRedactor` (one class per data type, each owns its regex and mask) · Context: `guard.RedactionStep` (walks the JSON result, picks the redactors that the agent's clearance requires from `GuardProperties.redactionByClearance`) · Data type enum: `SensitiveDataType` | **One regex that masks everything the same way** — cannot keep a different hint per type (`r***@example.com` vs `017******78`) and cannot hide only some types per clearance. **`if (type == EMAIL) … else if (type == PHONE) …` inside the step** — works, but every new data type edits the step and its tests (violates Open/Closed). |
| **Observer** | FR6 — a breached limit raises an alert that is stored in PostgreSQL, and later features (notifications, audit) must react without the limit code knowing about them. FR8 — when a kill switch is turned on, FR4 approvals must cancel their pending requests (TODO, see `docs/limits-and-kill-switch.md`). | Publisher: `limits.LimitStep` publishes `limits.LimitBreachedEvent` (first breach per window only) · Subscriber: `limits.AlertService` (`@EventListener`, stores an `Alert`) · Publisher: `admin.KillSwitchService` publishes `admin.KillSwitchActivated` (OFF → ON only) · Subscribers: none yet (the approvals module will add one) | **Call the alert service directly from `LimitStep`** — simplest, but the limit code then knows about alerts, and every new reaction (email, webhook, audit) edits the limit code (Open/Closed). **A message queue (Kafka, RabbitMQ)** — decouples across processes, but adds a container on an 8 GB laptop for one JVM; in-process events are enough for now. **Spring `@Async` listeners** — would make the 429 response wait less, but a lost alert would then be invisible; kept synchronous until a listener is slow. |
| **Strategy** | FR3 — argument conditions in policies (`amount ≤ 2000`, `id` matches the end user …); new kinds of conditions must be addable without touching the engine. | Strategy: `policy.operator.ConditionOperator` · Concrete strategies: `EqualsOperator`, `NotEqualsOperator`, `LessThanOrEqualOperator`, `GreaterThanOrEqualOperator`, `InOperator`, `MatchesEndUserOperator` · Context: `policy.PolicyEngine` (picks the operator by the `operator` name in the rule JSON; Spring injects all operator beans) | **`switch (operator)` inside the engine** — shorter, but every new operator edits and re-tests the engine, and per-operator value checks/explanations end up scattered. **A general expression language (SpEL)** — very flexible, but an admin-written expression can call arbitrary methods (security risk in a security product) and is hard to validate or explain in a deny message. |
| **State** | FR4 — an approval request has a lifecycle (PENDING → APPROVED / APPROVED_WITH_EDITS / REJECTED / EXPIRED / CANCELLED) and illegal moves (approve an expired request, decide twice) must be refused with 409. | State interface: `approval.ApprovalStateBehavior` (every transition throws by default) · Concrete states: `PendingState` (allows all 5 transitions), `ApprovedState`, `ApprovedWithEditsState`, `RejectedState`, `ExpiredState`, `CancelledState` (final: allow nothing) · Context: `approval.ApprovalRequest` (stored `ApprovalState` enum maps to its behaviour object) · Error: `IllegalApprovalTransitionException` (409) | **`switch (state)` in the service** — every new state or action edits one big switch and is easy to get wrong silently. **Boolean flags (`approved`, `expired`…)** — allow impossible combinations such as approved AND expired. |
| **Observer** | FR4 — a new approval request must notify an approver (web page + webhook) without the pipeline step knowing who listens; FR8 — a kill switch must cancel pending approvals; FR7 (later) — audit listens to `ApprovalRequested`/`ApprovalDecided`. | Events: `approval.ApprovalRequested`, `approval.ApprovalDecided`, `admin.KillSwitchActivated` · Observers: `ApprovalWebhookNotifier` (after commit, own virtual thread, errors swallowed), `ApprovalWaiters` (after commit, wakes the held agent call), `ApprovalKillSwitchListener` (cancels covered PENDING requests) · Publisher: `ApprovalService`, `KillSwitchService` | **Call the notifier / waiter directly from the service** — a slow or dead webhook would then block decisions, and FR7 would have to edit the service. **Message queue** — an extra container for one JVM. |
